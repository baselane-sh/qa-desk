# qa-desk Phase 2 (Runs) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish the runs and executions model and the Runs view: close a run, record evidence and a per-execution environment and locale, show status counts per run, show cross-run status on the Cases list, and give the case history real content that refreshes as you work.

**Architecture:** Phase 1 already ships the append-only runs and executions stores, the loopback `node:http` API and the static Runs view. Phase 2 adds three model functions (`closeRun`, `runSummary`, plus a widened `validateExecutionPatch`), three API changes (a close route, a `summary` field on run responses, `latestByRun` on the case list, run names on history) and a set of small pure helpers in the browser modules so the UI logic is testable in Node with no DOM.

**Tech Stack:** Node 22+ ESM (`.mjs`), `node:test`, `node:http`. No npm dependencies. Vanilla HTML, CSS and ES modules in the browser.

**Spec:** `docs/superpowers/specs/2026-09-12-qa-desk-design.md` (phase 2 is the "Delivery order" item 2: full runs and executions model, Runs view, history, keyboard).

## Global Constraints

- Node 22 or later. `"type": "module"`, every file `.mjs`, relative imports carry the `.mjs` extension.
- No npm dependencies. No build step. The UI ships finished as static files.
- Every source file under 800 lines. Functions under 50 lines where practical.
- Immutability: never mutate a record or array in place. JSONL stores are append-only, latest record per key wins on read, malformed lines are skipped with a warning, files are never rewritten.
- Every child process runs through `execFile` or `spawn` with an argv array and `shell: false`. Text from the user reaches a CLI as an argument or stdin, never through a shell.
- Every enum value on a record must come from the config lists. Config is validated on every command; a bad config prints every problem and exits 1.
- No product-specific names in source. No client data (cases, results, fixtures, logs) enters this repo.
- Text in the UI and in messages: plain English, no em dashes.
- UI never uses `alert`, `confirm` or `prompt`.
- Commit after every task with a message that says why. The commit snippets below omit the trailer for brevity; every real commit ends with the trailer line `Claude-Session: https://claude.ai/code/session_01LTSFXjdR7zhPyiuszGDhDb`.
- Tests: `node --test 'skills/qa-desk/test/*.test.mjs'` from the repo root. Child processes are injected in tests; no test calls `gh`, `bd`, `claude` or `codex`. Task 9 is the one exception and runs `git` in a temporary directory.

## Starting point

Phase 2 builds on the phase 1 code after the review fixes land. The review fixes
change five files that several tasks below also touch:

- `scripts/lib/jsonl.mjs`: a per-path write queue, so two appends to the same file cannot interleave.
- `scripts/lib/runs.mjs` and `scripts/lib/validate.mjs`: an execution patch must carry a `status` when the case has no execution yet in that run. Every first `PUT /api/runs/:id/executions/:caseId` in this plan therefore sends a `status`, and Task 4 keeps the detail editors locked until a status exists.
- `scripts/lib/defect-body.mjs`: the fence around quoted text is chosen from the content. Task 3 states what to do whether or not that has landed.
- `scripts/server.mjs` and `scripts/lib/dispatch.mjs`: a dispatch queue.

Read the file you are about to change before you change it. For `runs.mjs`,
`validate.mjs`, `defect-body.mjs` and `server.mjs` the steps below are
insertions anchored on exact existing lines, not whole-file rewrites, so they
apply cleanly on top of the review fixes.

export async function closeRun(paths, id, { now = defaultNow } = {}) {
  const run = await getRun(paths, id);
  if (!run) throw new Error(`unknown run ${id}`);
  if (run.closedAt) throw new Error(`run ${id} is already closed`);
  const closed = { ...run, closedAt: now() };
  await appendJsonl(paths.runs, closed);
  return closed;
}

export async function runSummary(paths, run) {

}

### Spec ambiguities resolved

1. **An empty Evidence section is left out, not printed as `(none)`.** The spec
   marks Evidence optional, unlike Actual result which always prints. A defect
   body with an empty quoted block adds nothing for the fix agent.
2. **`latestByRun` carries a `null` for an open run that holds the case but has
   no execution yet.** The spec says "latest execution per open run attached".
   Keys for every open run that covers the case, valued `null` when untested,
   are what the "one small badge per open run" requirement needs. A run that
   does not hold the case gets no key at all.
3. **`runSummary` returns `{ total, executed, counts }`, not a pass rate.** The
   spec puts pass rate in Reports, which is phase 3. `executed` is
   `total - untested` and is what the run list badge and the header read.
4. **A status outside the five valid values counts as untested.** Only a
   hand-edited or malformed JSONL line can produce one, and validation never
   writes one, so the summary refuses to invent a sixth bucket.
5. **The status filter control did not exist inside a run.** The Runs view never
   rendered the Cases view filter pane, so `matchesFilters` supported a status
   filter with no way to set it. Task 6 adds the control to the run header;
   `matchesFilters` is unchanged.
6. **Detail editors are locked until a status exists.** The review fixes make an
   execution patch carry a status when the case has no execution in that run, so
   a blur-save of evidence, actual, duration, environment or locale on an
   untested case would fail with a 400. Task 4 disables those editors and says
   why in one line of UI text, rather than letting the person meet an error.
7. **Cross-run badges show in the Cases view only while no run is picked.** The
   brief keeps the `?runId=` response shape unchanged, and the app asks for
   `?runId=` whenever a run is selected. So the Cases list shows that run's own
   status then, and the per-open-run badges when no run is selected. Adding a
   deselect control would be a new UI affordance, which phase 2 does not cover.
8. **The run list badge refreshes when a run is picked, created or closed, not
   on every keypress.** The header strip is computed in the browser from the
   loaded cases, so per-keypress feedback costs no request.

### Type consistency checks

- `runSummary` in `scripts/lib/runs.mjs` (Task 5) and `countStatuses` in
  `public/views/runs.js` (Task 6) return the same shape,
  `{ total, executed, counts }`, with the same six `counts` keys, so
  `summaryLabel` reads either one. The two `SUMMARY_STATUSES` arrays are
  duplicated on purpose, with a comment in the browser copy, because a browser
  module cannot import from `scripts/lib`. Their contents are asserted in both
  the model test (Task 5) and the UI test (Task 6).
- `closeRun(paths, id, { now })` matches the `createRun(paths, input, { now })`
  and `recordExecution(paths, patch, { now, executedBy })` convention: `paths`
  first, the injected clock last.
- `paths` from `dataPaths` stays the single handle for every store function.
- Error strings are the contract between the store and the server: `unknown run`
  maps to 404, `is not in run` to 400, `is closed` and `already closed` to 409.
  Task 1 adds the last two and matches the existing regular expression style in
  `executionRoute`.
- `statusOf(c)` is the single source of a case's status in the browser and
  returns `untested` for a missing execution. `needsStatusFirst`,
  `countStatuses`, `runBadges`, `matchesFilters` and `defectHint` all agree on
  that word.
- The execution record shape is `{ runId, caseId, status, actual, evidence?,
  env, locale, executedBy, executedAt, durationSec?, defectId? }`. `evidence` is
  the only new field, spelled the same in `validateExecutionPatch` (Task 3), the
  execution panel (Task 4) and `buildDefectBody` (Task 3).
- `GET /api/cases` returns `latestByRun` and never `execution`;
  `GET /api/cases?runId=` returns `execution` and `defectId` and never
  `latestByRun`. Both are asserted in Task 7's server test, and `runBadges`
  returns an empty array for the second shape so `renderList` serves both views.
- `historyLine(h)` reads `runName`, which only the history route adds (Task 8).
  It falls back to the run id, so a history record from a run whose JSONL line
  is missing still renders.
